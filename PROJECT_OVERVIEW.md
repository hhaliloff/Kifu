# Kifu — обзор проекта и фактического состояния

Документ описывает состояние репозитория по исходникам на **25 сентября 2026 года**. Это самостоятельный обзор проекта: существующие `KifuDesignSystem.md`, `Resources/KataGo/NOTICE.md` и содержимое `graphify-out/` не заменяются и не редактируются.

## Обновление 27 сентября 2026 года

После первоначального аудита добавлена локальная история партий в `Application Support/KifuGames.json`. Игра с ботом сохраняется после каждого хода; прежний `lastGameSGF` переносится в историю при первом запуске новой версии. В библиотеке можно открыть любую сохранённую или импортированную партию, перемещаться по ходам, экспортировать SGF до выбранного хода, отправить позицию на анализ или продолжить игру с ботом. Во время текущей партии просмотр ходов и экспорт доступны из игрового экрана.

Импорт теперь читает коллекции SGF и варианты как отдельные линии, сохраняет изменения расстановки `AB`/`AW`/`AE` между ходами и `PL` для стороны следующего хода. Экран анализа позволяет менять расстановку и экспортировать либо исходную линию, либо отредактированную позицию как SGF с установочными камнями. Размеры доски по-прежнему ограничены поддерживаемыми приложением 9×9, 13×13 и 19×19; при экспорте варианта сохраняется выбранная линия, а не всё исходное дерево SGF.

Важно различать наличие реализации в исходниках и проверенное поведение приложения: ниже функциональность помечена как **реализовано в коде**, **ограничено/частично** или **не обнаружено**. Статический аудит кода сам по себе не подтверждает работу на устройстве.

## Кратко

Kifu — нативное iOS-приложение на SwiftUI для игры в го, обучения, задач и локального анализа. Основная структура приложения находится в `Sources/Kifu`, правила и часть игрового поиска — в самостоятельном Swift-пакете `Packages/GoCore`, а сильный локальный движок — вендорный KataGo, подключаемый через C/C++ GTP bridge. Предусмотрена офлайн-работа движка: модель и конфигурация находятся в ресурсах приложения, сетевой AI в проверенном игровом пути не обнаружен.

Это не AlphaGo и не локальная LLM. Для AI используется KataGo с компактной нейросетью; объяснения тренера — заранее написанные шаблонные фразы и простая логика выбора объяснения, а не генеративная языковая модель.

## Экраны и пользовательские сценарии

В `ContentView` организованы пять основных вкладок: главная, обучение, задачи, библиотека и профиль. Из главной доступны начало игры, обучение, задача и ручной анализ позиции. Дополнительные сценарии открываются как экраны/листы: настройка игры, игровая доска, просмотр подсчёта, AI-разбор, повтор позиции, импорт SGF и анализ.

- **Игра:** параметры выбираются в setup-экране. Игровая модель проверяет легальность хода, поддерживает захват и отображает счётчики. Для японского подсчёта пользователь вручную отмечает мёртвые группы; можно вернуться к игре.
- **Обучение:** урок показывает заданную позицию и принимает ход на доске. После верного ответа профиль отмечает урок завершённым.
- **Задачи:** правильный ход завершает фиксированную tsumego-позицию. Решение дневной задачи обновляет соответствующую статистику и streak.
- **Библиотека:** системный импортёр принимает SGF-файл размером до 5 МБ. Доступен экспорт SGF последней партии.
- **Профиль:** можно изменить отображаемое имя и язык интерфейса; статистика сохраняется на этом устройстве.

Доска реализована в `GobanView.swift` средствами SwiftUI/Canvas, без отдельного игрового UI-фреймворка. Она рисует линии, hoshi, камни, последний ход, опциональную подсветку liberties и отметки мёртвых групп; присутствует VoiceOver-сетка. Для 19×19 обычное касание использует выбор точки с повторным подтверждением.

## Архитектура и движение данных

```text
SwiftUI Views (Sources/Kifu/ContentView.swift, GobanView.swift)
            │ действия пользователя / состояние экранов
            ▼
AppModels.swift ─────── UserDefaults (локальный профиль и счётчики)
       │                 └─ последний SGF партии
       ├── правила и оценка ──► GoCore (Packages/GoCore)
       │
       └── запрос хода/анализа ─► KataGoEngine actor (Swift)
                                      │ C API / GTP-команды
                                      ▼
                               GTPBridge.cpp (worker thread)
                                      │
                                      ▼
                             KataGo static library + MPSGraph
                                      │
                         модель и cfg из Bundle приложения
```

### GoCore

`Packages/GoCore` — Swift-пакет без внешних Swift-зависимостей. Основные компоненты: `Board`, `Types`, `Zobrist`, `Handicap`, `Scoring`, `GameRecord`, `SGF`, `EngineAPI`, `MCTS` и `Playout`. Размеры доски ограничены поддерживаемыми 9/13/19. MCTS — эвристический UCT/RAVE-поиск с playout и не является основным современным AI приложения.

Есть два замечания к правилам/вспомогательному поиску, которые следует учитывать при развитии:

1. GoCore MCTS использует area scoring даже для Japanese ruleset; это ограничение не описывает native KataGo-поиск, которому правила передаются отдельно.
2. `GameRecord` по умолчанию задаёт komi 7.5 даже при Japanese ruleset, хотя для него указано значение 6.5. Вызывающий код должен явно передать корректное значение, пока API не будет исправлен.

### KataGo и офлайн-режим

Вендорная версия — KataGo v1.18.2 (commit `3c144b3`), с лицензией исходников MIT и отдельными лицензиями зависимостей. Для iOS проект собирает KataGo как статическую библиотеку и использует `Vendor/KataGo/cpp/ios/GTPBridge.{h,cpp}`: движок работает внутри процесса приложения в отдельном worker thread, а не как запускаемый desktop-процесс. Swift actor лениво загружает конфигурацию и модель из Bundle и передаёт команды через bridge. Для поиска используются ограничения по времени и числу визитов; конфигурация не включает ponder/resign.

В ресурсах находится сжатая сеть `kata1-b10c128-s1141046784-d204142634.txt.gz` (NOTICE указывает CC0 для модели) и `Kifu-iOS.cfg`. iOS-конфигурация рассчитана на MPSGraph/GPU-путь; Core ML conversion stub в этой сборке недоступен. Наличие сетевого API для игрового AI в проверенном пути не найдено. Наличие исходников, bridge и модели подтверждено; фактический runtime на физическом iPhone, скорость первой инициализации, термальный режим и качество игры отдельно не измерялись.

## Правила окончания и подсчёт

- После двух последовательных пасов приложение открывает этап подсчёта.
- Chinese ruleset использует area scoring: камни на доске плюс окружённые пустые пункты; заданный komi — 7.5.
- Japanese ruleset считает территорию и пленных и позволяет вручную помечать мёртвые группы; заданный komi — 6.5.
- Автоматическое предположение о мёртвых группах — эвристика по размеру/свободам и не заменяет подтверждение спорной позиции игроками.
- В скоринговом коде комментарий и фактический порог эвристики расходятся: комментарий говорит о `≤ 2× размера` и `≤ 12 пунктов`, код сравнивает с `max(12, 2× размера)`. Это стоит сверить и покрыть отдельными тестами.

## SGF: фактический охват

SGF-парсер поддерживает коллекции FF[4], дерево вариантов, неизвестные свойства и прямоугольники точек с ограничениями на размер входа (5 МБ), глубину (128) и число узлов (50 000). Writer умеет сериализовать дерево. Преобразование SGF в текущий `GameRecord` берёт первую игру и главную линию; UI показывает конечную позицию, а не полноценный навигатор по дереву. Некоторые изменения расстановки камней в середине партии (`AE`, `AB`, `AW`) отклоняются. Неизвестное значение SGF `RU` в текущем преобразовании молча трактуется как Chinese.

## Данные профиля и приватность

Профиль хранится локально через `UserDefaults.standard`: имя, выбранный язык, числа партий/побед/решённых задач/уроков, счётчик запусков, ID завершённых уроков, дата последней дневной задачи и строка последнего SGF. Счётчик запусков увеличивается при создании профиля; win rate вычисляется из общего количества игр и побед. Streak обновляется через дневную задачу. Отдельной базы партий, синхронизации между устройствами, логина или облачного профиля в проверенном коде нет.

Отображаемое звание вида `Nk` выводится из простой формулы по wins/puzzles/lessons и не должно восприниматься как официальный рейтинг или оценка Glicko/Elo. Значки достижений — пороговые визуальные отметки, а не отдельная полноценная reward-система.

`PrivacyInfo.xcprivacy` декларирует отсутствие tracking и собираемых типов данных, а также использование UserDefaults с reason code CA92.1. Перед публикацией декларацию следует повторно сверить с фактическим составом SDK и финальной сборкой.

## Языки и дизайн

В `Localization.swift` вручную заданы русские, английские, корейские, японские и китайские строки; выбранный язык хранится в профиле. При отсутствующем ключе используется English fallback. В XcodeGen-конфигурации локализации в основном не заведены как отдельные resource catalogs, и в существующих языковых таблицах требуется отдельный аудит полноты/смешения языков. В дальнейшем лучше проверять покрытие ключей тестом и рассмотреть String Catalog, не смешивая этот технический обзор с уже существующей дизайн-спецификацией.

Визуальная система описана в `KifuDesignSystem.md`; SwiftUI-компоненты задаются через `DesignSystem.swift`, графический фон содержит `InkLandscape`. Текущий основной стиль — светлая бумага/лак и азиатские мотивы; `ContentView` принудительно включает светлую цветовую схему, поэтому упомянутые в спецификации варианты темы нельзя считать реализованными только на основании документа.

## Сборка и запуск

Основной источник конфигурации проекта — `project.yml`; `Kifu.xcodeproj` генерируется XcodeGen. `m.xcodeproj` является старым/неполным: в нём отсутствуют часть связки KataGo, bridge/header и ресурсов, поэтому открывать его как актуальный проект Kifu не следует.

Для сборки требуются Xcode/Apple toolchain, XcodeGen, CMake и Ninja. Скрипт `Scripts/build-katago-ios.sh` запускается как pre-build phase и строит статические библиотеки для выбранной платформы в DerivedData. Анализ конфигурации указывает, что эта phase запускается при каждой сборке, а число параллельных задач по умолчанию ограничено тремя.

Из корня репозитория:

```sh
xcodegen generate
xcodebuild -project Kifu.xcodeproj -scheme Kifu \
  -destination 'generic/platform=iOS Simulator' \
  CODE_SIGNING_ALLOWED=NO build

swift test --package-path Packages/GoCore
```

Для сборки под устройство можно заменить destination на `generic/platform=iOS`. `CODE_SIGNING_ALLOWED=NO` годится для компиляционной проверки, но не для установки/публикации; запуск на устройстве требует настроенной Apple Development Team и provisioning. Поскольку настройки команды разработчика не заданы в каноническом `project.yml`, локальную signing-команду следует настраивать в Xcode и не полагаться на невоспроизводимое значение в сгенерированном pbxproj.

## Проверки и текущие проблемы сборки

В `Packages/GoCore/Tests/GoCoreTests` находятся тесты правил доски, координат/форы, MCTS, скоринга и SGF (всего 60 макросов `@Test` по статическому подсчёту). Отдельного набора UI-тестов и специальных интеграционных тестов C bridge/KataGo не обнаружено. Testables схемы `Kifu` не подключают GoCore автоматически, поэтому пакетные тесты запускаются отдельной командой выше.

При предыдущей CLI-проверке исходники компилировались для симулятора и iOS device при отключённой подписи; это подтверждает сборку, но не успешное открытие приложения и не runtime-поведение. Живой запуск симулятора и тесты тогда не выполнялись. В Xcode на предоставленном скриншоте показаны две независимые проблемы: отсутствует выбранная Development Team для подписи, а `Command PhaseScriptExecution` завершилась с ненулевым кодом. Скриншот не содержит лога pre-build phase, поэтому конкретная причина сбоя KataGo build script по нему не установлена. Для диагностики нужен полный Report Navigator log этой phase; signing issue отдельно исправляется выбором команды в Signing & Capabilities.

Также стоит проверить asset каталоги перед релизом: ревью обнаружило `AppIcon` без назначенного файла изображения. Результат финальной archive validation не проверялся.

## Чего пока нет или что не подтверждено

- Полный и проверенный разбор всей партии с классификацией ошибок по ходам.
- Объяснения AI на естественном языке, построенные из полного набора причин позиции; нынешние фразы шаблонные.
- Большой адаптивный курс, большая библиотека tsumego и прогресс сложности задач.
- Полный SGF-вьювер с деревом вариантов, пошаговой навигацией и архивом партий.
- Реальный рейтинговый алгоритм, серверный аккаунт и синхронизация статистики.

## Рекомендуемый порядок следующих проверок

1. Получить полный лог Xcode pre-build phase и устранить фактическую причину `build-katago-ios.sh` failure; отдельно настроить signing team в Xcode.
2. Запустить `swift test --package-path Packages/GoCore`, добавить тесты на японский komi, японский MCTS/скоринг, завершение после пасов и спорные мёртвые группы.
3. Проверить чистую сборку и запуск на реальном iPhone: первый запуск KataGo, время ответа, память, нагрев, отмена поиска и возврат приложения из background.
4. Добавить интеграционный тест GTP bridge и smoke-тест bundled model/config, чтобы проверять не только компиляцию.
5. Провести аудит всех ключей локализации для пяти языков и запретить неявные English fallbacks для видимых строк релизных экранов.
6. Исправить/добавить AppIcon и пройти Archive/Validate с настроенной командой разработчика.
7. Затем наращивать содержание и архитектурные функции (история партий/SGF tree/review по ходам), сохраняя ограничения офлайн-режима и отсутствие локальной LLM.
